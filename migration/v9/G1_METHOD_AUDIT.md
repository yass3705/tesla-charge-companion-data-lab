# G1 — audit technique des méthodes existantes

Audit commencé le 20 octobre 2026. Cet audit lit uniquement le dépôt et ses données historiques. Il ne vérifie aucun nouveau prix ni endpoint fournisseur. Les constats intermédiaires ci-dessous sont datés ; la décision de porte courante est à la fin.

## Inventaire reproductible

`python3 scripts/v9_rebuild_inventory.py --output migration/v9/legacy-inventory.json` produit un registre statique de 1 207 workflows et 756 fichiers historiques dans `scripts/` ; les outils créés pour cette reconstruction sont exclus du décompte. Il conserve, pour chaque YAML, les scripts nommés, les noms de secrets, les chemins de données explicites et les événements déclencheurs. Les valeurs de secrets ne sont jamais extraites. Parmi les 756 scripts, 43 ne sont pas cités littéralement par un YAML ; cela n'établit pas qu'ils sont inutiles. Plusieurs portent des méthodes ou contrôles directs, notamment GeniePoint UK, Lidl UK, Ze-Watt et Zephyre. Ils restent dans la revue G1.

`python3 scripts/v9_scheduled_methods.py --output migration/v9/scheduled-methods.json` produit la matrice des 117 workflows planifiés. Chaque ligne garde les commandes exactes détectées, les scripts, les secrets nommés, les chemins de fichiers et la portée. Le contrôle exige 117/117 lignes avec au moins une commande. Les 117 méthodes ont une **destination proposée** répartie sur 76 modules logiciels candidats, en regroupant les workflows d'un même fournisseur. `destination_module` reste vide tant que la méthode et ses sorties n'ont pas été qualifiées ; ces chemins proposés ne prouvent pas la migration. Trois YAML n'ont aucun chemin de fichier littéral détecté ; l'un est le collecteur REVE, dont le répertoire est défini par `REVE_DATA_DIR=data/spain_reve/full_20261018` et `scripts/reve_es_stream_collect.py`. Les deux autres sont une maintenance Actions et une validation historique.

| Catégorie observable | Nombre | Conséquence pour la migration |
| --- | ---: | --- |
| Workflows planifiés | 117 | Revoir les commandes et sorties comme méthodes de collecte candidates. |
| Planifiés avec permission ou commande d'écriture | 115 | Aucun ne peut être réactivé tel quel pour la nouvelle architecture. |
| Déclenchés par `workflow_run` | 16 | Éliminer les chaînes indirectes de la nouvelle architecture. |
| Workflows sans pays unique déductible | 367 | Résoudre par les sources et sorties ; ne pas déduire un pays d'un seul nom de script partagé. |
| Planifiés sans pays unique déductible | 26 | Portée et rôle relus dans `scheduled-scope-review.json` ; certains sont transversaux ou multi-pays. |
| Planifiés sans référence `scripts/` ou `src/` détectée | 13 | Lire le YAML complet : commande inline ou binaire externe possible. |

Le champ `country_hint` est un indice, pas une provenance validée. Le champ `contains_write_command_or_permission` est conservateur : il détecte aussi une permission d'écriture sans commande de push. Le registre ne classe pas encore les méthodes comme utiles ou obsolètes et ne certifie pas G1.

Les 26 cas planifiés sans pays unique ont une portée documentée dans `scheduled-scope-review.json`. Le contrôle automatique exige l'égalité exacte entre cette liste et les 26 cas du registre. Les outils transversaux ont une portée vide plutôt qu'une attribution fictive aux neuf pays. `validate-v9-country-progress.yml` reste une **ancienne validation** comportant des constantes de volume ; elle ne doit pas être reprise dans les nouvelles portes.

Une branche Production locale distincte `rebuild/v9-20261020` a été créée au SHA distant `fba450da9092450fa7315d4c5b44e7e80394c8b4`, sans modifier la branche historique ni le site. `scripts/v9_production_consumers.py` a comparé les 1 469 chemins de fichiers détectés dans les YAML Data Lab à 176 fichiers de code/configuration Production : 80 chemins ont une référence littérale, et les 80 fichiers existent dans le `main` Data Lab examiné. La liste exacte est dans `production-consumers.json`. Les références dynamiques et les pins historiques ne sont pas prouvés par ce test ; un chemin cité dans un test n'est pas forcément chargé par le runtime. La revue des méthodes doit donc suivre la chaîne de build réelle avant de classer une source comme non utilisée.

Parmi les 1 090 workflows sans `schedule`, 61 citent un de ces chemins référencés par Production. `scripts/v9_manual_consumer_priority.py` les extrait dans `production-linked-manual-workflows.json` pour une revue prioritaire ; aucun de ces 61 ne référence un script manquant. Les 1 029 autres ne sont **pas** classés inutiles : une sortie peut être résolue dynamiquement ou conservée dans un snapshot historique. Aucune suppression ne résulte de ce tri.

Le [registre central provisoire](source-registry.json), généré par `scripts/v9_source_registry.py`, associe les 117 planifiés, 61 manuels liés littéralement à Production et 43 scripts sans référence YAML, soit 221 méthodes prioritaires, à 108 modules candidats. Le contrôle exige une destination proposée pour chacun des 43 scripts isolés. Il regroupe les portées, noms de secrets et chemins connus. Les chemins de module sont des destinations **proposées** ; aucun module n'est encore déclaré migré. Les 1 029 autres workflows restent explicitement répertoriés dans `legacy-inventory.json` et attendent la revue de leur utilité. Le registre est un outil de conservation et de tri, pas une preuve de collecte ou de consommation Production.

Une matrice supplémentaire [script-destinations.json](script-destinations.json) propose un rattachement logiciel pour **756/756 scripts historiques**, y compris ceux des workflows manuels non prioritaires. `scripts/v9_script_destinations.py` exige un et un seul module candidat par script et s'arrête si le nombre de scripts change. Les 18 scripts appelés par plusieurs familles de workflows ont une destination explicite dans le générateur ; une revue des noms génériques a corrigé les rattachements évidents vers des faux CPO comme `france`, `audit`, `nl` ou `owner`. Cette matrice couvre la préservation des fichiers, **pas** la qualification de leur rôle ni leur exécution future. Les 1 029 wrappers YAML restants doivent encore être classés avant G1.

**536 workflows** ne citent aucun script `scripts/` ou `src/` : leur méthode est entièrement ou partiellement inline dans le YAML. [inline-methods.json](inline-methods.json) conserve pour chacun le chemin, le commit d'archive `0b1b9d754`, le SHA-256 du YAML, les secrets nommés, chemins de sortie détectés et module candidat. Aucun YAML n'a changé depuis ce commit (`git diff --name-only ... -- .github/workflows` vide). Le tri par chemins de fichiers avait omis des sorties `data/` dynamiques et une base IZIVIA conservée hors de `data/`. La lecture du corps YAML a corrigé ces omissions. Le tri final est 23 critiques (planifiées ou littéralement liées à Production), 147 candidates à données et 366 références historiques. Ces catégories ne prouvent pas l'exécution des méthodes.

Les 23 méthodes critiques ont maintenant une [classification explicite](inline-critical-review.json) basée sur les étapes et sorties des YAML : collecteur, compilateur/réconciliation, audit de référence ou maintenance historique. Les 23/23 entrées sont contrôlées contre la liste critique générée, et leur code inline reste archivé à l'identique. Cela n'exécute pas ces méthodes et ne valide pas leurs sorties.

Les 147 candidates à données ont une [classification par rôle](inline-data-review.json) après lecture des noms d'étapes et des chemins YAML. Les cas dont le nom induisait un mauvais rôle (par exemple les oracles ChargePoint qui récoltent aussi des fichiers exacts, la validation des frais différés, l'inventaire IONITY, les deux bases IZIVIA et la sonde Shell UK qui collecte) ont des corrections explicites dans le générateur. Le résultat est une **classification d'inventaire**, pas une certification des sorties ni de la compatibilité d'exécution.

Les 366 restantes ont une [classification historique](inline-historical-review.json) : 28 références de validation et 338 méthodes expérimentales archivées. Chaque ligne garde le commit, l'empreinte du YAML et les noms d'étapes. Ces workflows ne sont ni planifiés, ni liés littéralement à Production, ni porteurs d'un chemin `data/` détecté ; un contrôle des `git add` a aussi promu les deux bases IZIVIA hors `data/`. Leur code reste restaurable depuis le commit d'archive. Ils ne sont pas proposés comme nouvelles collectes actives.

`python3 scripts/validate_v9_g1.py` est le contrôle automatique actuel. Il vérifie l'égalité de l'inventaire avec tous les YAML présents, la destination unique des 756 scripts, la représentation des neuf pays plus Tesla et les empreintes/classes des 536 méthodes inline. Le 20 octobre, ces contrôles ont réussi mais **G1 a échoué uniquement sur les deux extracteurs Ubitricity NL absents**. Aucun passage en G2 n'est autorisé par ce résultat.

## Contrat Ubitricity NL incomplet dans `main`

Le workflow planifié `ubitricity-nl-payg-refresh.yml` invoque deux fichiers absents : `scripts/audit_nl_ubitricity_payg_portal.py` et `scripts/reconcile_nl_ubitricity_payg_overlay.py`. `git log --all --full-history` et les autres arbres locaux consultés ne fournissent pas ces fichiers. Le commit de création `2930717c8` n'a ajouté que le YAML ; le commit `e166b409d` a ajouté le candidat et `scripts/integrate_ubitricity_nl_payg.py`, sans les deux extracteurs. Ainsi, le workflow hebdomadaire ne peut pas réussir depuis le `main` actuel. Il reste désactivé avec l'ensemble des Actions.

La [PR historique #151](https://github.com/yass3705/tesla-charge-companion-data-lab/pull/151) décrit le rapprochement exact et la collecte hebdomadaire, mais sa liste de fichiers confirme aussi l'absence des deux extracteurs. Un seul essai technique en lecture seule sur une URL de portail déjà enregistrée dans le candidat a répondu HTTP 200 ; le HTML contient les connecteurs et grilles dans une sérialisation JavaScript côté serveur. Cette observation de **format** ne fournit pas le code d'origine et n'est ni une nouvelle enquête tarifaire ni une vérification des montants. Aucun prix issu de cette réponse n'a été intégré au dépôt.

La méthode et la donnée validées ne sont pas perdues : le YAML conserve les commandes et paramètres, `dotnl_netherlands_build.py` et `integrate_ubitricity_nl_payg.py` compilent, et `data/operator_direct/ubitricity_nl_payg_exact_overlay_candidate.json.gz.b64` se décompresse et contient 3 tarifs et 3 670 correspondances exactes. Sa politique exige la source portail officiel, le canal Direct, les identités EVSE/connecteur exactes et exclut la préautorisation du prix. Cela prouve l'existence de l'artefact historique, **pas** la récupérabilité des deux extracteurs manquants ni la fraîcheur de ses montants.

Test technique lecture seule : `python3 scripts/integrate_ubitricity_nl_payg.py --no-write` sur le `normalized.json.gz` et le candidat du `main` actuel a réussi (`status=validated_no_write`, 3 670 correspondances exactes promues en mémoire, 0 rejet, 4 lignes source ambiguës exclues, 3 grilles). Ce test confirme le fonctionnement de l'intégrateur sur ces **entrées identiques** ; il n'établit ni un nouveau prix ni l'exécution du collecteur manquant. Aucun fichier de données n'a été modifié.

Décision G1 : la méthode d'acquisition est classée `legacy_method_unavailable` dans [legacy-method-exceptions.json](legacy-method-exceptions.json). Le candidat historique et l'intégrateur restent préservés dans `cpo/ubitricity`, mais l'acquisition hebdomadaire reste désactivée. Le YAML et le candidat en donnent les entrées, sorties et politiques, sans spécifier entièrement la désérialisation du portail et la résolution des conflits ; une réimplémentation équivalente ne peut donc pas être démontrée avec les seules preuves archivées. Aucun montant nouveau n'est extrait ni promu. Le validateur admet uniquement les deux chemins manquants nommés, leur YAML et candidat épinglés par SHA, et refuse toute autre absence.

La recherche ciblée supplémentaire dans les références Git accessibles (`git log --all` et branche historique `origin/codex/nl-ubitricity-direct-payg`) n'a pas trouvé ces deux scripts. La recherche locale par noms exacts était déjà négative. Une future restauration exige le code d'origine ou un contrat de format approuvé et des fixtures suffisantes. Cette limite isolée ne bloque plus à elle seule G1.

## Décision G1 — PASS de l'inventaire et des destinations

Le registre définitif est [method-dispositions.json](method-dispositions.json), généré par `scripts/v9_g1_method_dispositions.py` à partir de [script-workflow-evidence.json](script-workflow-evidence.json) et des registres précédents. Il couvre **1 207/1 207 workflows et 756/756 scripts** avec destination, disposition, empreinte de code/YAML, scripts invoqués, noms de secrets et chemins disponibles. Les 221 méthodes prioritaires sont couvertes ; les 43 scripts sans workflow sont maintenus. Les 536 méthodes inline conservent leur revue et leur archive SHA propres. Le registre initial `source-registry.json` demeure un index de candidats et ne constitue plus la décision finale.

La classification s'appuie sur les déclencheurs, les commandes et chemins `git add`, les artefacts Actions, le contenu des scripts, les chemins de données et les références Production. Un chemin cité dans un YAML ou dans le code n'est pas présumé être une sortie : les méthodes ambiguës restent `retain_*_partial_method` et inactives jusqu'aux tests G2. Les wrappers n'ayant que des sorties de rapport ou de documentation et aucun lien Production sont archivés ; leur code reste dans l'historique. Les méthodes dormant avec données sont conservées sans planification automatique. **Aucun de ces statuts ne signifie qu'une collecte fonctionne déjà.**

Le constructeur Production `scripts/build_snapshot.py` emploie aussi des répertoires et glob dynamiques (`data/national/uk_*`, `*italy*`, plateformes eMSP). Une comparaison ciblée a trouvé 65 chemins littéraux dans ce constructeur, dont 35 absents de l'inventaire YAML : 12 existent déjà dans Data Lab et restent préservés, un appartient à Production, les 22 autres sont notamment des sorties du constructeur ou des chemins conditionnels. Les méthodes produisant ou lisant des données nationales et de plateforme ont été conservées par prudence, même sans référence littérale exacte. Ce contrôle ne démontre pas la consommation runtime de chaque source ; G4 la testera.

Tests de porte : génération répétée des deux registres avec comparaison octet par octet ; `python3 scripts/validate_v9_g1.py` **PASS** (1 207 workflows, 756 scripts, 536 inline, dix périmètres) ; dix tests ciblés des exceptions et décisions de classement **PASS** ; compilation des scripts de validation **PASS**. L'exception Ubitricity reste indisponible et désactivée, son dernier candidat conservé. Il n'y a ni recherche ni promotion de prix nouveaux. Les sorties partielles et les dépendances runtime sont explicitement reportées aux tests G2/G4 ; G1 valide la préservation et l'orientation des méthodes.
